## Q1. Observers, EntityEvent, propagation, observer entities and cleanup; component hooks; relationships

### Takeaway
In 0.20 every observer is matched on an `EventPattern`. Every `Event` is an `EventPattern`, and lifecycle events are now the generic patterns `Add<B>`, `Insert<B>`, `Discard<B>` (formerly Replace), `Remove<B>` and `Despawn<B>`. `On<'w,'t,E: EventPattern>` is the observer param. Observers are entities, they record what they watch in `ObservedBy`, and an observer despawns itself once every entity it watches has despawned. Hooks are `fn(DeferredWorld, HookContext)` with `on_add/on_insert/on_discard/on_remove/on_despawn`. Relationships (`Relationship`/`RelationshipTarget`, `linked_spawn`) keep their 0.16+ shape.

### Inferences
- Observer entities plus `ObservedBy` auto-cleanup give a free "effect disposal" model. An effect that `watch_entities` its signal entities dies when all its sources die. The rule is all, not any, so an effect that must die when its owner dies needs an explicit relationship (e.g. a custom `EffectOf` with `linked_spawn`).
- Because `Observer` cannot be retargeted, dynamic dependency tracking (where the deps of a derived value change between runs) is better done with a library-owned relationship or edge component than by mutating the observer's watched set.
- Signals as `#[component(immutable)]` components with `Insert`/`Discard` observers yield exact, push-based change notification without polling `Changed<T>`. This is the officially documented way to get "OnMutate" semantics.
- Observer commands are deferred until all queued observers finish (#19569), so chained derived-value propagation through Commands happens in waves within one flush. The library should avoid assuming read-after-write inside one cascade, or should use `DeferredWorld`/exclusive access.

## Q2. BSN in 0.20 (bsn!, Scene/Template, patches, inheritance/composition, spawn_scene, embedded values/closures)

### Takeaway
BSN is a code-first macro system. `bsn!` builds a `Scene`, which resolves into a `ResolvedScene` of `Template`s and related scenes. Field-level patches are layered in order, `@scene` includes compose, and `{expr}` embeds Rust values. `on(closure)` attaches entity observers, and `SceneComponent` with props gives React-like components. There is no built-in reactivity: scenes are spawn-time only. `apply_scene` on an existing entity "replace[s] and orphan[s] the current entity's children".

### Inferences
- A reactive library integrates most natively as Templates (`template(|ctx| ...)` or a custom `Template` impl) and `on(...)` observers placed inside `bsn!`. A `bind(signal, |v| Component)` helper can be a `Template` whose `build_template` inserts the initial value and spawns an observer or effect entity watching the signal.
- Reactive lists cannot rely on re-applying scenes, because `apply_scene` orphans existing children. Keyed list diffing must spawn and despawn per-item child scenes itself, e.g. with `queue_spawn_related_scenes::<Children>` per new item and `insert_related` for ordering.
- `Ready` is the right hook for effects that need the full subtree to exist.

## Q3. Change detection (Ref, Changed, Tick, DetectChanges) and cost; any "component change observers" in 0.20?

### Takeaway
Change detection is still pull-based and tick-based: per-component `added`/`changed` ticks are compared against each system's `last_run`. New in 0.20 is an opt-in `#[component(summary_tick)]` column-level tick so queries can skip unchanged columns. There is still no mutation observer for mutable components; the docs point to immutable components plus `Insert`/`Discard` as the "OnMutate" pattern.

### Inferences
- Polling `Changed<T>` is O(matching entities) per system run. `summary_tick` makes "nothing changed this frame" nearly free for table components, which helps a system-based "pull" reactive scheduler. Per-entity cost on frames where something did change is unchanged.
- For fine-grained push-based signals, immutable components (re-inserted on write) plus `Insert` observers are the most ECS-native approach. Each write is an archetype-stable re-insert that fires hooks and observers. It is not free, but it is exact.
- `set_if_neq` / `replace_if_neq` are the built-in equality guard for avoiding spurious downstream recomputation.

### Gaps

## Q4. bevy_ui_widgets / bevy_feathers state and value binding

### Takeaway
Headless widgets are deliberately controlled (external state, MVC/React-style). They emit `ValueChange<T>` / `Activate` entity events as change requests. The app writes the state-bearing component (`Checked`, `SliderValue`, `SelectedTab`, …), and the widget reacts to that component being inserted or replaced. Optional `*_self_update` observers make a widget uncontrolled. Feathers widgets are BSN `SceneComponent`s with props and are restyled via `Changed<...>` systems and `On<Insert<Theme*>>` observers.

### Cited Findings
- Crate docs: "almost all of the widgets use **external** state management … These widgets emit a `ValueChange` event which carries the proposed new state; the app should respond … by updating its own internal model, and by updating the widget state … the widget state is contained in a specific state-bearing component (like `SliderValue`), and the widget detects when this component is inserted or replaced." The model is React "controlled" widgets. Exceptions: buttons and menu items emit `Activate`, text inputs self-manage their (expensive) state, and scrollbars write the scroll position directly. `checkbox_self_update` etc. "effectively converts it into an 'uncontrolled' widget". ### Inferences
- A two-way binding helper maps naturally onto this design. Signal → widget: on signal change, insert `SliderValue(v)` / `Checked`, or trigger `SetSliderValue`. Widget → signal: an observer on `On<ValueChange<T>>` writes the signal, optionally only when `is_final`, and calls `propagate(false)` per the "consume what you use" rule. Do not also attach `*_self_update`, or the state is written twice.
- Since `SliderValue` is immutable, writing it fires `Insert`/`Discard`. A reactive library can observe widget state push-style instead of polling.

### Gaps
- The exact 0.18/0.19 history of the widget callback API (e.g. any `Callback`/`SystemId` props that existed before the observer-only design) was not verified.
- I did not audit every widget's state component (list, menu, select, text input).

## Q5. What Bevy maintainers have said about the reactivity direction

### Takeaway
The canonical statement is still cart's July 2024 next-gen scene/BSN discussion (#14437). It describes fine-grained, observer-style reactivity layered additively on ECS change detection, hooks and observers. It names branching, loops and child add/remove as the hard part, and calls viridia's bevy_reactor/quill a "proven path". As of 0.20, upstream Bevy has shipped no reactivity layer. The 0.20 roadmap lists `.bsn` assets, assets-as-entities, Template-powered required components and mutually exclusive components, not reactivity.

### Cited Findings
- Cart (Jul 22, 2024): reactive BSN is "still largely an open question". Fine-grained, observer-style reactivity is "the only viable strategy for a general purpose reactive system in the context of Bevy", because it builds on change detection, operates on ECS values, uses hooks and observers, and is an "additive layer". The prototype tied reactivity to components (`require`s `React(counter)`) and re-ran reactive BSN parts in topological order. Top-level field reactivity is the "easy part"; branching, looping and adding/removing children are hard. Cart sketched `for item in .items` syntax. Reactive scenes outside UI were expected to be niche — [bevy discussion #14437](https://github.com/bevyengine/bevy/discussions/14437)
- Cart named viridia's bevy_reactor ("a general purpose fine-grained reactive framework for Bevy ECS"), obsidian_ui, and quill ("coarse-grained") as "a 'proven path' that we should learn from" — [#14437](https://github.com/bevyengine/bevy/discussions/14437)
- Cart (Aug 8, 2024): "the current system doesn't exist to be a full reactive tree-diff system". Whether patches can drive reactivity is "an open question". "I think slots are probably the right path forward, especially in the context of reactivity". Start "with direct-observers". Editing entities "the normal way" should be allowed but "discouraged in the context of reactive scenes" — [#14437](https://github.com/bevyengine/bevy/discussions/14437)
- Viridia (Jul 25, 2024): "The slot-based approach is much more robust". Templates should be a "formula" of constants and variables whose output is a "black box". Solid.js `<For>` diffs by data items, so "no need for an explicit 'key' attribute". Community members (CooCooCaCha, hymm) argued that keys or identity are needed for reordering and animation — [#14437](https://github.com/bevyengine/bevy/discussions/14437)
- UkoeHB (bevy_cobweb) argued for reactors "decoupled from 'figuring out what to react to'" in a hooks/observers style — [#14437](https://github.com/bevyengine/bevy/discussions/14437)
- Cart (2025, Reddit): he was testing a replacement for the `Construct` trait aimed partly at "playing nicer with reactivity". The baseline should be flexible enough to support multiple reactive paradigms so the ecosystem can experiment. This is a secondary report via search snippet and I could not open it directly — [Reddit thread (mirror)](https://redlib.hbubli.cc/r/rust/comments/1kt03fc/bevy_jam_6/mtrslik/?context=3)
- 0.20 "What's Next": `.bsn` asset format, Assets as Entities ("so they can use observers, relationships, and BSN"), remote inspector, "More powerful required components" via `Template` integration, mutually exclusive components, and HDR. Reactivity is not listed — [Bevy 0.20 news](https://bevy.org/news/bevy-0-20/)
- Ecosystem reactive crates: haalka (futures-signals based, "eventually consistent", reactions may lag a frame or more) and jonmo ("Bevy-native reactive signals" maintaining a dependency graph of Bevy systems traversed each frame) — [haalka docs](https://docs.rs/crate/haalka/0.5.0), [jonmo docs](https://docs.rs/crate/jonmo/0.1.1)
- bevy_reactor repo: "Fine-grained reactive framework for Bevy" (viridia). The README was not accessible via fetch — [github.com/viridia/bevy_reactor](https://github.com/viridia/bevy_reactor)

### Inferences
- The upstream direction (Template replaced Construct, BSN patches, observers in BSN, `Ready`, immutable components) is consistent with cart's "flexible baseline, ecosystem experiments" stance. A third-party library built from Templates, observers and relationships is aligned with that direction and is likely to stay compatible.
- Keyed vs data-identity list diffing was contested and never resolved upstream, so the library has free design room there.

### Gaps
- I found no 2025–2026 primary-source statement (GitHub discussion, issue or working group) from cart, alice-i-cecile or viridia that updates the 2024 position. I also could not confirm whether a formal "reactivity working group" exists. Searches returned nothing.
- I could not confirm whether bevy_reactor has been upstreamed or targets 0.20. The repo page shows no README content, and there is no evidence of upstreaming in the 0.20 notes.

## Q6. Recommended ECS-native patterns vs anti-patterns

### Takeaway
Bevy's own docs and code favor these patterns: state in components, with immutable components for exactly-observable state; observers (entity-scoped, self-cleaning) for push reactions; hooks only for structural invariants; relationships for entity graphs, with `linked_spawn` for ownership and teardown; Commands/deferred application; and BSN Templates for spawn-time construction. Discouraged: general logic in hooks, relying on immediate command application inside observer cascades, retargeting observers, mutating `RelationshipTarget` collections directly, and per-`&mut` mutation hooks.

### Cited Findings
- Hooks "are intended to be used for structural side effects … not intended for general-purpose logic". Examples given are cached indexes, resource cleanup, and keeping hierarchies in sync — [lifecycle.rs ~100-110](file:///C:/Users/Computer/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/bevy_ecs-0.20.0/src/lifecycle.rs)
- Observers are "not treated as an 'innate' part of component behavior", can be added or removed at runtime, and multiple observers are allowed per event — [distributed_storage.rs:178-185](file:///C:/Users/Computer/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/bevy_ecs-0.20.0/src/observer/distributed_storage.rs)

### Inferences
- Suggested mapping for a reactive library:
  - **Signal**: an entity holding an immutable value component.
  - **Derived value**: an entity whose dependency edges are a custom relationship (e.g. `DependsOn` → `Dependents`).
  - **Effect**: an `Observer` entity, or a `SystemHandle`-backed one-shot system, owned through a `linked_spawn` relationship so owner despawn tears it down.
  - **Binding**: a BSN `Template` plus observer.
  - **Reactive list**: keyed child management via `insert_related`/`despawn_related`.
- Because resources are now entities, global signals can become resource entities that are observable like any other entity. `Insert` observers on resource components should work in principle, but this was not verified.
- `register_tracked_system` gives RAII-style lifetime for effect systems, which avoids leaked `SystemId` entities.

### Gaps
- I did not verify that lifecycle observers (`On<Insert<R>>`) fire for resource components stored on resource entities in 0.20.
- I found no official "anti-patterns" page for reactivity. The anti-patterns above are drawn from API doc warnings.
